## 1. Ausgangslage & Problembeschreibung

Der Pull Request [#4494](https://github.com/contextra/contextra/pull/4494) (*"fix(mcp): gate mock provider branch behind test-utils feature"*) hatte das primäre Ziel, `mock`-Matches in `crates/contextra-mcp/src/config.rs` hinter das Feature `test-utils` zu stellen.

Beim Merge von PR #4494 wurden jedoch **152 Dateien** geändert und **-11.563 Zeilen Netto-Diff** erzeugt, darunter **71 gelöschte Dateien** (unter anderem Kern-Komponenten, Audit-Dokumente und Testdateien wie `.github/workflows/wiring-check.yml`, `.jules/tasks/*`, `crates/contextra-crypto/src/deletion_proof/*`, `crates/contextra-vector/tests/hnsw_slot_reuse_ghost_edges.rs` sowie `xtask/src/wiring_check/mod.rs`).

Obwohl der PR alle damaligen CI-Checks und Merge-Gates erfolgreich bestand und automatisch gemergt wurde, bricht seit dem Merge der Aufruf:
```bash
cargo check --workspace --all-targets --locked
```
auf dem `main`-Branch ab mit Kompilierfehlern in `crates/contextra-engine/src/lib.rs` (`ContextraError` nicht importiert, assoziierte Typen `Candle`/`Ollama` fehlen).

---

## 2. Ist-Ablauf & Ursachenanalyse

### 2.1 Warum lief kein vollständiger Compile-Check auf dem PR-Merge-Resultat?

1. **Unvollständige Prüfung in Merge Gate (`merge-gate.yml`):**
   - Das schnelle, PR-blockierende Merge Gate (`.github/workflows/merge-gate.yml`) führt in `compile-security-check` nur `cargo clippy --workspace --lib --bins --locked -- -D warnings` aus.
   - `--all-targets` (welches Tests, Benchmarks und Beispiele kompiliert) wird im `merge-gate.yml` **nicht** aufgeführt. Dadurch blieben kaputte/gelöschte Test- und Benchmark-Referenzen im PR unbemerkt.

2. **Entkopplung & Nicht-Blockieren des Haupt-CI-Workflows (`rust-ci.yml`):**
   - In `.github/workflows/rust-ci.yml` existiert zwar der Job `compile-check` (`cargo run -p xtask -- check-compile`), welcher `cargo check --locked --workspace --all-targets` ausführt.
   - Dieser Job ist jedoch im `verdict.yml` (Aggregate Verdict Gate) **nicht als required/blocking Gate hinterlegt**. In `governance/verdict-required.toml` fehlen `compile-check` oder `rust-ci.yml` komplett in den blockierenden Regeln.

3. **Inkompatibilität durch veralteten Branch-Stand (Outdated Merge-Base):**
   - PR #4494 basierte auf einer veralteten Merge-Base (`30fe0ba4`), auf welcher `crates/contextra-engine` noch mit älteren Interfaces kompilierte oder der Stand lokal funktionierte.
   - Nach dem Parallel-Merge anderer PRs veränderte sich `main`. Weder `merge-gate.yml` noch `verdict.yml` erzwangen ein Rebase / ein Freshness-Check der Branch-Merge-Base vor dem Merge.
   - Da GitHub Merge Queues oder Merge-Resultat-Checks (`github.event.pull_request.merge_commit_sha`) nicht strikt vorgeschrieben waren, wurde die Kombination aus veralteten Löschungen und neuem `main`-Code ohne frischen Test auf dem finalen Merge-Commit zusammengeführt.

---

### 2.2 Welche Gates haben die Löschung von 71 Dateien gesehen?

Sowohl `scope-guard` als auch `diff-budget` liefen im Rahmen von `verdict.yml` über die xtask Harness-Befehle:
```bash
cargo xtask scope-guard --json --base <base> --head <head>
cargo xtask diff-budget --json --base <base> --head <head>
```

Die Gates haben die Änderungen physisch registriert, wurden aber aus folgenden Gründen **nicht ausgelöst (False Positives / Silent Pass)**:

#### Schwachstelle bei `scope-guard` (`xtask/src/harness/scope_guard.rs`)
- `scope-guard` prüft, ob geänderte Dateien laut einer zugehörigen Task-Card (`.jules/tasks/<CARD>.toml`) im erlaubten `scope` liegen oder `forbidden` berühren.
- PR #4494 besaß **keine Task-Card** und kein `--card` Argument.
- Der Code in `scope_guard.rs` verhält sich bei fehlender Task-Card wie folgt:
  - Wenn `card_mode == "optional"`, wird der Status `not_applicable` mit Exit-Code `0` ausgegeben.
  - Das `verdict`-Harness wertet `not_applicable` bzw. Exit-Code 0 als **erfolgreich / bestanden** (`pass`) aus!
- Dadurch passierte eine Massen-Löschung ohne Scope-Zuordnung das Gate völlig ungehindert.

#### Schwachstelle bei `diff-budget` (`xtask/src/harness/diff_budget.rs`)
- `diff-budget` berechnet das Budget aus den Feldern `files`, `lines` und `crates`.
- Ohne explizite Task-Card greifen Fallbacks: `max_files = 15`, `max_lines = 600`, `max_crates = 2`.
- **Der entscheidende Fehler in `diff-budget`:**
  `diff_budget_get_numstat` filtert Dateien aus, die von `diff_budget_is_excluded` erfasst werden. Jedoch berechnet `git diff --numstat` bei gelöschten oder umstrukturierten Dateien nur Zeilen.
  Wenn ein PR massiv Dateien löscht, ohne dass sie durch die Ausschlussliste gefiltert werden, lag die Zeilenzahl bei -11.563 Zeilen. Standard-Diff-Budgets unterscheiden oft nicht sauber zwischen *hinzugefügten/geänderten* Zeilen und *rein gelöschtem Legacy-Code*.
  Des Weiteren kann, falls im PR-Body ein Marker gefälscht/nicht validiert wurde, das Budget umgangen worden sein.

---

### 2.3 Warum lag ein Versagen der Schutzlogik (Task-Scope vs. Diff vs. Ledger) vor?

1. **Grenzen des Jules Worktree-Hash-Ledgers (REFACTOR_PLAN §7):**
   - Der Worktree-Hash-Ledger (`cargo xtask ledger`) bescheinigt fälschungssicher, dass ein definierter Satz an Prüfungen in der VM/Sandbox des Agenten auf dem Commit `HEAD` erfolgreich ausgeführt wurde.
   - **Das fundamentale Limit:** Ein Ledger bescheinigt nur den Zustand zur Ausführungszeit im isolierten Branch. Er **schützt prinzipbedingt nicht** vor:
     a) Einem nachträglichen Merge, wenn sich `main` zwischenzeitlich weiterbewegt hat (Stale Merge-Base).
     b) Unvollständigen Test-Abdeckungen in der Test-Suite der VM (z. B. wenn `cargo check --all-targets` in der VM gar nicht aufgerufen wurde).

2. **Fehlende Entkopplung von Massen-Löschungen:**
   - Es gab keine Regelung, die großflächige Löschungen (> N Dateien oder > X % des Worktree-Inhalts) an eine manuelle Freigabe, ein explizites Governance-Label (z. B. `allow-mass-deletion`) oder ein verpflichtendes Refactoring-Task-Card gebunden hat.

## 3. Maßnahmenspektrum & Lösungsvorschläge (mit Aufwand)

| Maßnahmenpaket | Beschreibung & Umsetzung | Geschätzter Aufwand |
| :--- | :--- | :--- |
| **(a) Pflicht-Job `cargo check --workspace --all-targets --locked` im PR Merge-Gate & Verdict** | **1. Integration in `merge-gate.yml`:** Ergänzung eines expliziten Steps `cargo check --workspace --all-targets --locked` im Job `compile-security-check`.<br>**2. Aufnahme in `governance/verdict-required.toml`:** Pflicht-Eintrag `name = "compile-check"` mit `blocking = true`.<br>**3. Enforce Merge-Result Validation:** Ausführung auf `${{ github.event.pull_request.merge_commit_sha }}` oder Rebase-Stand. | **3h** (Gering) |
| **(b) Gate "Massen-Löschungen außerhalb des Task-Scopes" (`mass-deletion-guard`)** | **1. Neues xtask-Harness-Modul `mass_deletion_guard`:** Schlägt fehl, wenn `deleted_files > 10` ODER `deleted_lines > 500`, AUSSER:<br>&nbsp;&nbsp;- Eine valide Task-Card existiert und deckt alle gelöschten Pfade explizit ab, ODER<br>&nbsp;&nbsp;- Das PR besitzt das Governance-Label `governance:allow-mass-deletion`.<br>**2. Veto bei fehlender Task-Card:** Wenn keine Task-Card vorhanden ist, darf `scope-guard` bei PRs mit `deleted_files > 0` nicht auf `not_applicable` zurückfallen, sondern muss fehlschlagen (`STRICT_SCOPE_MODE`). | **6h** (Mittel) |
| **(c) Branch Merge-Base Freshness Gate (Gemäß REFACTOR_PLAN §7)** | **1. Ergänzung `check-merge-base-freshness` in `xtask`:** Prüft, wie viele Commits `origin/main` dem `merge-base(origin/main, HEAD)` voraus ist.<br>**2. Schwellenwert-Enforcement:** Wenn `main` neue Commits enthält, die berührte Crates/Dateien betreffen (oder generell > K Commits dahinter liegt), wird der Merge blockiert (`status = "fail", message = "Branch base is stale. Please rebase on latest origin/main"`).<br>**3. Invalidierung des Ledgers:** Verhindert das Wiederverwenden alter Ledger-Hashes auf veralteten Merge-Bases. | **5h** (Mittel) |

---

## 4. Fazit & Nächste Schritte

PR #4494 offenbarte eine Lücke in der Sicherheitsarchitektur: Blockierende Schnell-Gates verließen sich auf unvollständige Compiler-Aufrufe (ohne `--all-targets`), während die tiefen Prüfungen entkoppelt oder bei fehlender Task-Card stumm geschaltet waren.

Durch die Umsetzung der Vorschläge (a), (b) und (c) wird die CI-Pipeline gehärtet, sodass weder veraltete Merge-Bases noch unvollständige `cargo check`-Aufrufe oder unkontrollierte Massen-Löschungen in den `main`-Branch gelangen können.
