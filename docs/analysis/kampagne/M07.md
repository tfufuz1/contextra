## 2. Befund & Problemstellung

### 2.1 BELEGT am Clone-HEAD `8753ee3e`
In `crates/contextra-store/src/kv/segment.rs` (Z. 157) ist `KvSegmentManager::generate_deletion_proof` wie folgt implementiert:
```rust
pub fn generate_deletion_proof(&self, group_id: u64) -> Result<bool, ContextraError> {
    match self.config.delete_mode {
        KvDeleteMode::TombstoneOnly => Err(ContextraError::KvDeleteModeConfig(
            "Löschbeweis auf Key-Value-Seite ist ausschließlich für `CryptoShred`-Segmente möglich, niemals für `TombstoneOnly`.",
        )),
        KvDeleteMode::CryptoShred => {
            if !self.registry.was_group_ever_registered(group_id) {
                return Err(ContextraError::KvDeleteModeConfig(
                    "Löschbeweis unzulässig: Gruppe wurde nie registriert.",
                ));
            }
            let is_active = self.registry.is_key_active(group_id);
            Ok(!is_active)
        }
    }
}
```

### 2.2 Bewertung des Befunds
Ein blosser `bool`-Rückgabewert (`Ok(true)` / `Ok(false)`) ist **kein kryptographisch signierter oder extern verifizierbarer Löschnachweis**. Er dokumentiert weder den genauen Zeitpunkt, noch den Mandanten (Tenant), noch die betroffene Schlüssel-Gruppen-ID oder den Zustand der Audit-/Checkpoint-Kette. Für externe Audits (z. B. DSGVO Art. 17 / BSI TR-02102-1) ist dieser Rückgabewert nutzlos.

## 5. Entwurf der `DeletionProof`-Struct für den Store-Pfad [BELEGT / VERMUTET]

Um auf Store-Ebene (`contextra-store`) echte, kryptographisch signierte Löschnachweise auszustellen, definieren wir die Datenstruktur und Kanonisierung:

### 5.1 Struct-Definition (`KvDeletionProof`)
```rust
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct KvDeletionProof {
    /// Versionsnummer des KV-Löschbeweises (z. B. 3 für Ed25519)
    pub version: u8,
    /// Mandanten-ID
    pub tenant_id: TenantId,
    /// Betroffene Crypto-Shredding Schlüsselgruppe
    pub group_id: u64,
    /// Zeitstempel der Schluessel-Destruktion in Unix-Nanosekunden
    pub timestamp_nanos: u64,
    /// Optionaler Blake3-Hash des aktuellen AuditChain/Checkpoint-Kettenkopfs
    pub chain_head_hash: Option<[u8; 32]>,
    /// Optionales RFC-3161 Timestamp-Token/Anchor fuer externe Zeitstempel
    pub anchor: Option<Vec<u8>>,
    /// Verifizierender oeffentlicher Ed25519-Schluessel (32 Bytes)
    pub public_key: [u8; 32],
    /// Ed25519-Signatur ueber die kanonisch codierten Bytes (64 Bytes)
    pub signature: [u8; 64],
}
```

### 5.2 Signaturschema & Kanonisierung (Längenpräfix gegen Kollisionen)
Die zu signierende Byte-Sequenz `canonical_bytes` wird streng mit 8-Byte-Längenpräfixen (Big-Endian `u64`) konstruiert, um Ambivalenzen und Hash-Kollisions-Attaken zu verhindern:
```
[domain_tag: "CONTEXTRA_KV_DELETION_PROOF_V3"][version: u8]
[tenant_id: u64]
[group_id: u64]
[timestamp_nanos: u64]
[len(chain_head_hash): u64][chain_head_hash: 0 oder 32 Bytes]
[len(anchor): u64][anchor: N Bytes]
```

### 5.3 Schlüsselhaltung (`proof_key_env.rs` / `CONTEXTRA_DELETION_PROOF_KEY`)
Der Signaturschlüssel für Löschnachweise wird aus der Umgebungsvariablen `CONTEXTRA_DELETION_PROOF_KEY` (Fallback `CONTEXTRA_PROOF_KEY`) geladen. In `contextra-mcp` existiert bereits das Modul `proof_key_env.rs`. Bei Nicht-Vorhandensein in der Produktion schlägt die Erzeugung fehl (kein Silently-Generated Fake-Proof).

## 7. Ehrliche Grenzen des Löschnachweises (DPO-Erklärung) [BELEGT]

Was beweist ein kryptographischer Löschnachweis (`KvDeletionProof` / `DeletionProof`) **NICHT**?

### 7.1 Formulierung für Datenschutzbeauftragte (DPO) (3 präzise Sätze)

> **1.** Der kryptographische Löschnachweis bestätigt die logische Entwertung des Verschlüsselungsschlüssels (Crypto-Shredding) im flüchtigen KeyRegistry-Speicher sowie die Protokollierung des Löschereignisses, garantiert jedoch nicht die physische Überschreibung von Datenresten in unterliegenden Betriebssystem-Caches (Block-Cache, Page-Cache) oder RAM-Puffern von Vektor- und Graph-Indizes.
>
> **2.** Auf physischen Speichermedien (SSD/NVMe) verhindert die Hardware-Ebene durch Wear-Leveling und Out-of-Place-Writes die unmittelbare physikalische Bit-Löschung verkapselter SBL/LSM-SSTable-Dateien, weshalb die Vertraulichkeit gelöschter Daten nach der Schlüsselvernichtung ausschließlich auf der mathematischen Unknackbarkeit der AES-256-GCM-SIV Verschlüsselung beruht.
>
> **3.** Der Löschnachweis erstreckt sich nicht auf historische unveränderliche Offline-Backups, katastrophensichere Desaster-Snapshots oder externe Replikations-Knoten, die vor dem Löschzeitpunkt erstellt wurden und gemäß den vorgegebenen Retention-Policies separat bereinigt oder durch Schlüssel-Rotation unlesbar gemacht werden müssen.
