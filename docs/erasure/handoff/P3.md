## 1. Ist-Befund zu den bestehenden Modulen

### Analyse der Dateien in `src/purge/`
1. `src/purge/window.rs`:
   - Enthaltene Typen/Funktionen: `WindowOutcome`, `run_window(cx: &PurgeCx)`, `run_core_window(core: &ErasureCore)`.
   - Modul-Doku beschreibt feste Schichtreihenfolge gemäß ER-20:
     a) Snapshots widerrufen (SnapshotRevoker)
     b) Textsegment-Rewrite
     c) Memtable-Drain, Flush, WAL-Segmente
     d) SSTable-Rewrite, F-Slots nullen, unlink
     e) Vektor-Kantenreparatur
     f) D-Slots der Zielmenge entfernen, F-Waisen prüfen
     g) Cache-Eviction
   - Befund: Es existierte bisher keine explizite Enum `PurgePhase` in `contextra-erasure`. Phasen waren implizit in der Ausführungsreihenfolge oder in `ErasureCore` verteilt.

2. `src/purge/order.rs`:
   - Enthaltene Typen/Funktionen: `PurgePriority` (Konstanten `SNAPSHOT_REVOKE`, `TEXT_REWRITE`, `WAL_FLUSH`, `SSTABLE_REWRITE`, `VECTOR_REPAIR`, `SLOT_CLEANUP`, `CACHE_EVICT`), `LayerPurgeOrder`, `sort_by_priority`.
   - Befund: Bildet Schichten auf statische Prioritäten ab, aber steuert nicht die Lebenszyklus-Phasen des Purge-Laufes.

3. `src/purge/reserve.rs`:
   - Enthaltene Typen/Funktionen: `ReserveCheck` (`Sufficient`, `Insufficient`), `check_disk_reserve`.
   - Befund: Prüft Plattenreserve vor dem Rewrite (ER-22, D-65).

4. `src/purge/cx.rs`:
   - Enthaltene Typen/Funktionen: `PurgeCx` (`deadline_nanos`, `min_free_bytes`, `batch_window`).
   - Befund: Ausführungskontext für Purge-Fenster; prüft Deadlines über `Clock`-Port.

### Analyse der Dateien in `src/scope/`
1. `src/scope/codec.rs`:
   - Magic `CTXSCOM\0` (8 Bytes), `scope_count` (u32 BE), Layer-Scopes.
   - Befund: Bisher kein explizites Versionsfeld und keine Prüfsumme im Header.
2. `src/scope/file.rs`:
   - Verwendet `FileHeader` (64 Byte Magic `CTXFILE\0`, Kind=9), BLAKE3-Header-MAC und AEAD-Envelope.
3. `src/scope/set.rs`:
   - `LayerScopeSet` und `ResolvedLayerScope`.
   - Befund: Es fehlte ein dedizierter Single-Flight Lock-Mechanismus für Scopes (INV-ERA-3) mit Epochen/Token-basierter Stale-Lock-Erkennung.

## 2. Phasen-Tabelle des physischen Purge (WP-2)

Gemäß der Spezifikation der Löschkette (insb. P09 / C5.1 / C5.6 / ER-20) gliedert sich der Lebenszyklus des physischen Purge in 9 aufeinanderfolgende Phasen:

| Phase | Code | Auslöser | Seiteneffekt | Fehlerfall |
|---|:---:|---|---|---|
| `Admitted` | 1 | Purge-Auftrag angenommen, Intent & Scope durable persistiert | Scope-Datei & Intent geschrieben, Vorbedingungen validiert | Scope-I/O-Fehler, ungültiger Scope → `PurgePhaseError::AdmissionFailed` |
| `Fenced` | 2 | Eintritt in geschützte Ausführung | Schreib-Sperre / Erasure-Fence auf Scope aktiv | Fence-Kollision, Lock belegt → `PurgePhaseError::FenceFailed` |
| `Flushed` | 3 | Vorbereitung des Rewrite | Aktive Memtables und In-Flight Puffer geflusht | Flush-I/O-Fehler → `PurgePhaseError::FlushFailed` |
| `Rewriting` | 4 | Beginn des Schicht-Rewrite | SSTables, Vektor-Segmente, Textsegmente ohne gelöschte Einheiten neu geschrieben | Plattenreserve erschöpft, I/O-Fehler → `PurgePhaseError::RewriteFailed` |
| `Disposing` | 5 | Abschluss des Rewrite | Obsolete Altdateien genullt (Scrub) und entsorgt (`unlink`) | Unlink/Scrub-Fehler → `PurgePhaseError::DisposeFailed` |
| `WalRetiring` | 6 | Entsorgung veralteter WAL-Segmente | WAL rotiert, Scope-bezogene Segmente entwertet | WAL-Sync-Fehler → `PurgePhaseError::WalRetireFailed` |
| `Witnessing` | 7 | Scanner-Prüfung | Messung & Erzeugung von `LayerWitness`-Einträgen | Positivkontrolle fehlerhaft, Restspuren → `PurgePhaseError::WitnessFailed` |
| `Finalizing` | 8 | Verankerung im Ledger | Ledger-Commit, Saga-Zustand avanciert | Ledger-Append scheitert → `PurgePhaseError::FinalizeFailed` |
| `Released` | 9 | Vollständiger Abschluss | Erasure-Fence freigegeben, Intent/Scope-Dateien aufgeräumt | Release-Fehler → `PurgePhaseError::ReleaseFailed` |

## 3. Getroffene Entscheidungen

1. **Einheitliche `PurgePhase` Enum (`src/purge/phase.rs`):**
   - Repräsentiert als `#[repr(u8)]` mit Codes `1..=9`.
   - Streng deterministische `can_transition_to(self, next)` Methode: Erlaubt ausschließlich denselben Zustand (Idempotenz) oder den exakt nächsten linearen Folgeschritt (`current + 1 == next`).
   - Code `0` sowie Werte `> 9` werden fail-closed abgelehnt.
2. **Fehlertaxonomie mit Phasenbezug (`PurgePhaseError`):**
   - Jeder Fehler ist getypt und einer Phase zugeordnet (`AdmissionFailed`, `FenceFailed`, `FlushFailed`, `RewriteFailure`, `DisposeFailed`, `WalRetireFailed`, `WitnessFailed`, `FinalizeFailed`, `ReleaseFailed`).
   - Keine Freitext-Strings als Fehlergrund.
3. **Dauerhafte Scope-Dateien mit Fail-Closed-Schutz (`src/scope/codec.rs` & `file.rs`):**
   - V2-Format mit 16-Bit Versionsfeld, 16-Bit Flags, 32-Bit Count und 32-Byte BLAKE3-Prüfsumme.
   - V1-Format bleibt für Abwärtskompatibilität lesbar.
   - Bitflips, Trunkierungen und MAC-/Prüfsummenfehler führen ausnahmslos zu `ErasureError::Corrupt` und niemals zu einer stillen leeren Rückgabe.
   - Atomares Schreiben via Vfs-Port (`write_atomic`, `sync_dir`).
4. **Single-Flight-Koordination (INV-ERA-3) via `ScopeLockManager` (`src/scope/single_flight.rs`):**
   - Lock-Dateien unter `scope/<erasure_id_hex>.lock` mit `CTXSLOK\0` Magic und BLAKE3-Checksumme.
   - Lease-Dauer und Stale-Lock-Erkennung ausschließlich über `Clock::monotonic_nanos`. Keine Wanduhr (`SystemTime`)!
   - Zombie-Prozesse können verwaiste Locks nach Ablauf der Lease nicht mehr irrtümlich freigeben (`EpochMismatch`), da die Epoche bei geordneter Übernahme inkrementiert wird.
5. **Resume-API für P9 (`src/purge/resume.rs`):**
   - `PurgeProgressTracker` zur Wiederherstellung von unterbrochenen Purge-Läufen (`recover`, `advance_to_next`, `next_phase`).

## 4. Exakte öffentliche Signaturen der neuen Komponenten

### `src/purge/phase.rs`
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash, Serialize, Deserialize)]
#[repr(u8)]
pub enum PurgePhase {
    Admitted = 1,
    Fenced = 2,
    Flushed = 3,
    Rewriting = 4,
    Disposing = 5,
    WalRetiring = 6,
    Witnessing = 7,
    Finalizing = 8,
    Released = 9,
}

impl PurgePhase {
    pub const fn code(self) -> u8;
    pub const fn is_terminal(self) -> bool;
    pub const fn can_transition_to(self, next: PurgePhase) -> bool;
    pub const fn next_phase(self) -> Option<PurgePhase>;
    pub fn must_run(self, target: PurgePhase) -> bool;
    pub fn transition_to(&mut self, next: PurgePhase) -> Result<(), PurgePhaseError>;
    pub fn from_code(code: u8) -> Result<Self, PurgePhaseError>;
}

#[derive(Debug, Error, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub enum PurgePhaseError {
    InvalidTransition { from: PurgePhase, to: PurgePhase },
    InvalidCode(u8),
    AdmissionFailed(AdmissionFailure),
    FenceFailed(FenceFailure),
    FlushFailed(FlushFailure),
    RewriteFailed(RewriteFailure),
    DisposeFailed(DisposeFailure),
    WalRetireFailed(WalRetireFailure),
    WitnessFailed(WitnessFailure),
    FinalizeFailed(FinalizeFailure),
    ReleaseFailed(ReleaseFailure),
}
```

pub struct PurgeProgressTracker {
    pub purge_id: [u8; 16],
    pub current_phase: PurgePhase,
    pub attempts: u32,
    pub last_phase_error: Option<PurgePhaseError>,

impl PurgeProgressTracker {
    pub fn new(purge_id: [u8; 16]) -> Self;

    pub fn next_phase(&self) -> Option<PurgePhase>;
    pub fn is_completed(&self) -> bool;
    pub fn advance_to_next(&mut self) -> Result<PurgePhase, PurgePhaseError>;
    pub fn record_failure(&mut self, err: PurgePhaseError);
}
